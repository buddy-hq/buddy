# Runtime Alignment Review

Date: 2026-04-22
Target commit: `dcf5e7a96` (`refactor(runtime): align Buddy with upstream and remove stale desktop/e2e`)
Upstream sync log: `/Users/prashantbhudwal/Code/buddy/docs/logs/upstream-fetch.2026-04-21.md`
Scope reviewed: `packages/buddy/src/**`, `packages/opencode-adapter/src/**`

## Status

Current verdict: the upstream runtime alignment commit introduced real Buddy regressions, but the concrete issues confirmed in this pass are now patched in the working tree.

The two fixes already present from the earlier review were real and I kept them:

1. Buddy tool wrappers now bridge upstream `Effect`-returning `ctx.ask()` / `ctx.metadata()` calls back to `Promise`s before Buddy tools `await` them.
2. Legacy migration repair is now best-effort during startup instead of being able to take the backend down on a transient SQLite lock.

I confirmed and fixed one additional regression in this pass:

3. Lesson-workspace file creation was still bypassing the upstream write runtime and writing directly with `node:fs/promises`.
4. Session prompt routing no longer preflighted session existence, so missing-session prompts could mutate Buddy teaching state and still return `200` with an upstream streamed error.
5. Runtime env bootstrap was importing Buddy global storage too early, so `Global.Path.*` ignored `BUDDY_RUNTIME_ROOT`.
6. Session routes no longer normalized malformed JSON into Buddy’s standard JSON error envelope.
7. Buddy custom learning tools were not actually unregistered when a tool group was disabled after being enabled once in the same directory.
8. Route schema-validation failures were still leaking the validator’s raw `{ success, error, data }` payload instead of Buddy’s standard JSON error envelope.
9. The added prompt/command preflight was incorrectly treating some real same-project sessions as missing and returning `404` before send.
10. Desktop quick-chat/logo rendering still assumed `buddy-icon.png` lived under the renderer asset root, which is false in the Electron runtime bundle.

## Findings

### Fixed: Buddy tool permission bridge was broken by the Effect runtime sync

Priority: P1

Problem:
- `packages/buddy/src/learning/tools/create-buddy-tool.ts` was forwarding the upstream `Tool.Context` object directly.
- In the new runtime, `ctx.ask()` and `ctx.metadata()` return `Effect`s.
- Buddy tools still use `await ctx.ask(...)` and `await ctx.metadata(...)`.
- `await` on an `Effect` object does not execute the effect, so tool permission requests silently stopped happening.

User-visible impact:
- Buddy-owned tools could read or write immediately without surfacing the intended permission request.
- This affected UX and safety for learning tools such as lesson-workspace operations and learner snapshot reads.

Fix status:
- Already present in the worktree when I started.
- Kept as-is after review.

Validation:
- `packages/buddy/test/session/abort-tools.test.ts`

### Fixed: Legacy migration repair could abort runtime startup on a transient DB lock

Priority: P1

Problem:
- `loadOpenCodeApp()` now runs the legacy migration repair before the server boots.
- That repair used a raw SQLite handle and could throw `SQLITE_BUSY`.
- A transient overlapping Buddy/OpenCode process could therefore block startup entirely.

User-visible impact:
- Intermittent startup failures during restart or overlapping runtime activity.

Fix status:
- Already present in the worktree when I started.
- Kept as-is after review.

Validation:
- `packages/buddy/test/opencode-runtime-legacy-migration-repair.test.ts`

### Fixed: lesson-workspace writes bypassed the upstream write tool

Priority: P1

Problem:
- `packages/buddy/src/learning/capabilities/lesson-workspace/tools/write-without-prompt.ts` was still calling `mkdir()` + `writeFile()` directly.
- That skipped the upstream write runtime’s formatting pass, watcher events, LSP refresh, and write-tool metadata.
- The helper existed specifically to avoid a second permission prompt, but it accidentally bypassed the rest of the upstream write behavior too.

User-visible impact:
- Newly created lesson files could miss refresh/diagnostic behavior that the rest of the app expects.
- This is the kind of subtle regression that feels like “the file exists but the editor/runtime did not fully notice.”

Fix:
- Added a small adapter seam at `packages/opencode-adapter/src/app-runtime.ts`.
- Reworked `write-without-prompt.ts` to initialize and execute the upstream `WriteTool` inside the current runtime instance.
- The helper now suppresses the duplicate prompt by providing a no-op `ask()` to the upstream tool while keeping the caller’s original Buddy permission gate.

Validation:
- Added `packages/buddy/test/learning/lesson-workspace-write-without-prompt.test.ts`
- Verified the helper now:
  - does not issue a second permission request
  - returns upstream write-tool metadata instead of the old hard-coded Buddy result
  - writes through the vendor runtime path successfully

### Fixed: missing-session prompts could leave Buddy state mutated while returning a streamed `200`

Priority: P1

Problem:
- `packages/buddy/src/session/orchestration/interaction-actions.ts` stopped checking that the target session exists before running Buddy’s prompt transform and proxying to the vendored runtime.
- The upstream `/session/:id/message` route can emit a `NotFoundError` inside the stream while keeping the outer HTTP status at `200`.
- Buddy had already written the next teaching session state and last outbound payload by that point, so the learner-facing session state drifted even though no real turn succeeded.

User-visible impact:
- Prompting a deleted or missing session could silently rewrite Buddy’s local teaching state.
- The request looked superficially successful at the HTTP layer while the actual error only existed inside the stream payload, which is bad UX for both the frontend and local recovery logic.

Fix:
- Added a prompt/command preflight using `assertSessionExistsInDirectory(...)` before any transform-side state mutation happens.
- Restored a regression test that verifies missing-session prompts now fail fast with `404` and preserve the previous teaching state.

Validation:
- `packages/buddy/test/session/route-regressions.test.ts`

### Fixed: runtime-root bootstrap no longer drifted back to the user home directory

Priority: P1

Problem:
- `packages/buddy/src/opencode-runtime/env.ts` imported `../storage`, which eagerly loaded `packages/buddy/src/storage/global.ts`.
- `storage/global.ts` computes its preferred XDG-backed paths at module evaluation time.
- Because that happened before `configureOpenCodeEnvironment()` set the runtime XDG env vars, Buddy global storage stayed pinned to the user-home defaults instead of the requested runtime root.

User-visible impact:
- Local runtime data/cache/state could escape the intended Buddy runtime root even when `BUDDY_RUNTIME_ROOT` was configured.
- That breaks isolation expectations for the embedded runtime and makes local state layout harder to reason about.

Fix:
- Narrowed the env bootstrap import to `../storage/constants` so it no longer initializes `storage/global.ts` before the XDG env vars are set.
- Restored the deleted runtime-env regression test that exercises the bootstrap order in a fresh subprocess.

Validation:
- `packages/buddy/test/opencode-runtime-env.test.ts`

### Fixed: malformed session JSON now returns Buddy’s standard `{"error": ...}` payload again

Priority: P2

Problem:
- Session routes rely on Hono’s JSON validator middleware.
- On malformed JSON, that middleware throws an `HTTPException` whose default response body is plain text: `Malformed JSON in request body`.
- Buddy previously normalized this case to `{ "error": "Invalid JSON body" }`, and the deleted regression tests stopped checking that contract.

User-visible impact:
- Frontend and local tooling now had to handle a one-off text/plain error shape on prompt/command routes instead of Buddy’s normal JSON envelope.
- This is small compared with the session-state bugs above, but it is still a UX/API regression.

Fix:
- Added an app-level `HTTPException` normalizer in `packages/buddy/src/index.ts`.
- Malformed JSON is now remapped back to `400` with `{ "error": "Invalid JSON body" }`.
- Restored the deleted prompt/command malformed-JSON regression tests and added missing-session no-state guards for both prompt and command routes.

Validation:
- `packages/buddy/test/session/route-regressions.test.ts`

### Fixed: disabled Buddy tool groups could stay registered in the active runtime

Priority: P1

Problem:
- `packages/buddy/src/learning/tools/register-buddy-tools.ts` kept `unregisterBuddyTools(...)` as a no-op from an earlier adapter state.
- The current adapter does expose `ToolRegistry.unregister(...)`, but Buddy never called it.
- If a directory enabled a Buddy-managed tool group such as `questionSet` or `flashcard` and later disabled it, the custom tool stayed present in the runtime registry for that directory.

User-visible impact:
- Config or capability changes could leave stale tools visible and callable even after Buddy believed they were disabled.
- This is especially risky around agent/runtime overlay sync, because the UI and config can say one thing while the actual tool surface still exposes another.

Fix:
- Rewired `unregisterBuddyTools(...)` to call the adapter’s real `ToolRegistry.unregister(...)`.
- Added focused runtime tests that cover same-directory disable-after-enable behavior and cross-directory isolation across runtime disposal/recreation.

Validation:
- `packages/buddy/test/learning/runtime-tool-registration.test.ts`
- `packages/buddy/test/config/opencode-overlay-isolation.test.ts`

### Fixed: route validation failures now normalize back to Buddy’s standard error envelope

Priority: P2

Problem:
- Buddy now normalizes malformed JSON exceptions, but schema-validation failures from `hono-openapi` validators still returned the library’s raw payload shape: `{ success: false, error: [...], data: ... }`.
- That bypassed Buddy’s documented and user-facing route contract of `{ "error": string }`.
- The inconsistency showed up immediately on permission-reply validation and could affect other validated routes too.

User-visible impact:
- Frontend and local clients had to special-case a second 400-error shape for ordinary form/body validation failures.
- This is a UX/API paper cut, but it is exactly the kind of response-shape drift that makes the app feel unreliable around config/permission flows.

Fix:
- Added a central post-route normalizer that rewrites standard-validator failure payloads into Buddy’s normal `{ "error": string }` envelope.
- The normalizer preserves the `400` status and derives a concise message from the first validation issue, including the field path when available.

Validation:
- `packages/buddy/test/permission/routes.test.ts`

### Fixed: prompt preflight could reject valid same-project sessions before send

Priority: P1

Problem:
- The new `assertSessionExistsInDirectory(...)` guard added extra project/directory reconciliation on top of a successful upstream `GET /session/:id`.
- In real desktop flows that was strict enough to reject valid sessions and turn prompt sends into immediate `404`s even though the session could still be fetched.
- This regression was introduced by the review patch, not by the original upstream alignment commit.

User-visible impact:
- Sending a message from an existing thread could fail immediately with `404`.
- The frontend recovery path then created a new session and could hit the same false-negative again, making chat feel completely broken.

Fix:
- Reduced the preflight back to a plain existence check against `GET /session/:id` in the requested directory.
- Kept the guard’s original purpose: fail fast for truly missing sessions before Buddy mutates teaching state.
- Added a regression test that proves same-project nested directories no longer get misclassified as missing on prompt routes.

Validation:
- `packages/buddy/test/session/prompt-preflight-regression.test.ts`

### Fixed: desktop Buddy icon URL now points at the packaged Electron icon instead of a missing renderer asset

Priority: P2

Problem:
- The web shell and Electron loading screens derived the Buddy logo URL from `assetBaseUrl` and assumed `buddy-icon.png` existed at the renderer root.
- In the Electron runtime bundle, that file is not present there, so the logo rendered as a broken image on the quick-chats entry screen and loading UI.

User-visible impact:
- The first-run / empty-chat surface showed a broken image in place of the Buddy logo, which is an obvious UX regression.

Fix:
- Electron now injects a concrete `iconUrl` that points at the packaged `resources/icons/icon.png` file.
- The first version of that fix over-applied the override in Electron dev too, which produced blocked `file://...` logo loads from the `http://localhost` renderer.
- Web/Electron logo helpers now only prefer `iconUrl` for `file:` renderer loads and fall back to the old public-asset resolution in dev.
- The desktop renderer config was still pointing `publicDir` at the pre-rename `packages/desktop/public` path, so the dev `buddy-icon.png` fallback had no backing asset after the move to `packages/desktop-electron`.
- Restored the old setup under the current package by serving `packages/desktop-electron/public` and restoring `buddy-icon.png` there.
- Added a small web regression test for the desktop override behavior.
- Added a desktop regression test that asserts the renderer public dir contains the Buddy icon.

Validation:
- `packages/web/test/static-asset.test.ts`
